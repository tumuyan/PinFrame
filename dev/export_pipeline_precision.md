## 1. 先纠正问题的提法

这件事最初被写成"消除预览与导出的亚像素差异"。**这个目标是错的**，三条理由都是结构性的：

1. **重采样算法不同且不可能相同。** 预览是 QPainter 的双线性；导出是 PIL 的 LANCZOS（缩放）+ BICUBIC（旋转）。即使几何完全对齐，像素值也不会一致。
2. **导出做两遍重采样，预览做一遍。** 导出先 `resize` 再 `rotate`，两次插值叠加；预览是单个仿射变换一次成像。导出天然更糊。
3. **预览本身不是"那张图"。** 预览叠了 `view_scale` 显示变换，`view_scale != 1.0` 时它在数学上就不可能与 1:1 导出逐像素相等。

而且用户不会把预览截图和导出文件做像素 diff。**这个目标既不可达，也不是需求。**

## 2. 客观需求是什么

按优先级重新表述：

| # | 需求 | 现状 |
|---|---|---|
| 1 | **帧间一致性** —— 导出序列内部不能出现数据里本不存在的抖动 | ❌ 有问题 |
| 2 | **尺寸可预测** —— UI 显示的目标分辨率 == 导出实际像素尺寸 | ✅ 成立，已被测试钉住 |
| 3 | **几何对齐一致** —— 预览里对齐好的，导出后仍对齐（允许重采样差异） | ✅ 基本成立 |

需求 1 直击产品核心价值。README 写的是"固定每一帧的大小和位置"、"预览和微调序列帧"——**帧间抖动正是这个工具存在的理由要消灭的东西**。

反过来说，**绝对偏移是无害的**：整个序列一致地偏 0.5px，动画看不出任何异常。所以优化目标应当是"帧间一致"，而不是"绝对精确"。

## 3. 实测数据

方法：用旋转对称的实心圆盘作夹具（真实质心恒在图像几何中心，已验证夹具偏移为 0），通过 `Exporter.compose_frame` 合成到 200×150 画布，测 alpha 加权质心。

**参考基准**：画布的像素索引中心是 `(W-1)/2 = 99.5`，**不是** `W/2 = 100`。（起草过程中一度用错基准，把 0.5px 误差读成 1px。）

### 实验 1：旋转序列（0°→30°，2° 步长，position=0）

| 源图 | 质心偏差范围 | 峰峰 | 相邻帧最大跳变 |
|---|---|---|---|
| 64×64（偶） | −0.500 .. −0.181 | **0.319 px** | 0.046 px |
| 63×63（奇） | −0.500 恒定 | **0.000 px** | 0.000 px |

奇数尺寸零漂移；偶数尺寸有 0.32px 的**平滑**漂移（PIL `rotate(expand=True)` 对偶数尺寸的半像素处理随角度变化）。相邻帧跳变仅 0.046px，**基本不可见**。

> 起草时曾假设"旋转序列会 ±1px 抖动"，**实测否定了这个假设**。旋转是三个量化源里最轻的。

**这是最严重的一项**：平移动画在预览里平滑，导出后变成"卡两帧、跳 1px"的阶梯。

### 严重度汇总

| 量化源 | 对需求 1 的影响 | 严重度 |

| 绝对居中 | 恒定 −0.5px，全序列一致 | 可忽略 |

## 4. 根因：一处架构限制 + 一处真 bug

### 居中公式是正确的

```python
dest = 画布中心 - 位图宽/2 + 偏移
```

代入验证：内容质心位于位图内 `(w-1)/2`，故 `(W/2 - w/2) + (w-1)/2 = (W-1)/2`，**恰好命中画布像素索引中心**。公式无误。

### 架构限制：整数贴图无法表达半像素落点

奇数宽度位图的理想落点必然是 `X.5`。用 `alpha_composite(img, (int, int))` 贴图，落点只能是整数，**±0.5px 误差无法避免**。

关键推论：**缩放渐变的 0.5px 交替是架构性的，任何取整函数都修不掉。** 因为位图宽度在奇偶之间交替，理想落点就在"整数"和"半整数"之间交替。

实测三种取整方式对实验 B 的影响：

| 取整方式 | 质心偏差范围 | 峰峰抖动 |
|---|---|---|
| `int()`（现状；正值等同 floor） | −0.5 .. 0.0 | 0.5 px |
| `round()`（banker's rounding） | −0.5 .. +0.5 | **1.0 px（翻倍变差）** |
| `floor(x + 0.5)`（half-up） | 0.0 .. +0.5 | 0.5 px |

`round()` 的进位方向取决于相邻整数的奇偶，而位图宽度本身也在奇偶交替，两个奇偶性互相干涉，把抖动放大一倍。**所以不能用 `round()`。**

### 真 bug：`int()` 在 0 处翻转取整方向

`int()` 对负数向零取整、对正数向下取整。当帧移出画布左/上边缘（`dest < 0`）时，取整方向翻转，平移动画在跨越边界处出现 1px 顿跳。

这一条与架构无关，是可以单独修掉的——见下节。

## 5. 已做的（方案 B 收窄版）

原本计划的"方案 B"是把 `int()` 换成 `round()`。**实测证明这会让缩放渐变的抖动翻倍**，因此方案 B 被收窄为它唯一站得住的部分：

- `int()` → `math.floor()`，并把整个"居中 + 取整"约定收进 `core.transform.composite_origin()`
- 对 `dest >= 0`（绝大多数情况）**输出完全不变**，故绝大多数导出产物不受影响
- 只修负坐标的方向翻转

配套测试（`dev/test_transform.py`）：

| 测试 | 锁定的性质 |
|---|---|
| `test_composite_origin_centers_content` | 偶数宽度落点精确命中像素中心 |
| `test_composite_origin_odd_width_is_half_pixel_limited` | 奇数宽度必然差 0.5px（把架构限制显式记录下来） |
| `test_composite_origin_uses_floor_not_truncation` | 负坐标必须 floor，不能向零取整 |
| `test_composite_origin_is_translation_consistent` | −60..+60 整数平移时落点步长恒为 1，无顿跳 |

**方案 B 不解决实验 A 的阶梯，也不解决实验 B 的交替。** 那两项只能靠方案 C。

## 6. 方案 C：单次仿射变换

把现在的四步管线

```
crop -> resize(LANCZOS) -> transpose -> rotate(BICUBIC, expand=True) -> 整数贴图
```

换成一次仿射变换，直接把源图重采样到画布坐标系：

```python
# 伪代码
matrix = 由 FrameGeometry 构造的逆仿射矩阵（含缩放、镜像、旋转、【分数】平移）
layer = src_img.transform((canvas_w, canvas_h), Image.Transform.AFFINE,
                          matrix, resample=Image.Resampling.BICUBIC)
canvas.alpha_composite(layer)
```

一次改动同时解决四件事：

- ✅ **分数位置真正平滑** —— 分数部分进入重采样，而不是被取整丢掉 → 需求 1 达成，实验 A 的阶梯消失
- ✅ **缩放奇偶交替消失** —— 不再有"中间位图"，也就没有奇偶宽度
- ✅ **偶数源图的旋转漂移消失** —— 不再依赖 `expand=True` 的 bbox 计算
- ✅ **画质提升** —— 两遍重采样变一遍，糊边减少

而且它让导出与预览在结构上同构（都是"一个仿射矩阵一次成像"），需求 3 自然变强。

矩阵可以直接由现有的 `FrameGeometry` 推导（`scale_x`/`scale_y`/`rotation`/`offset_x`/`offset_y` 已经齐备），这正是变换收敛到 `core/transform.py` 带来的便利。

## 7. 代价与未决问题

### 会改变所有导出产物

不可避免，且是一次性的。建议作为显式的"导出精度与画质改进"发版，写进 changelog 并附前后对比图，**不要混在重构里悄悄改**。

### 未决问题：`effective_target_size()` 在新管线下的含义

这是方案 C 最需要设计的一点，**不是随手能改的**。

现在的语义链条是：

```
effective_target_size() = int(基准尺寸 × scale ÷ aspect_ratio)
                        == exporter 中间位图的尺寸
                        == 属性面板/时间轴显示的"目标分辨率"
```

方案 C 取消了"中间位图"，于是"目标分辨率"失去了它当前对应的物理实体。需要决定：

- **选项 1**：保留 `effective_target_size()` 作为"名义目标分辨率"，仅供 UI 显示与用户输入换算，不再声称等于任何实际像素产物。需求 2 的表述要相应弱化。
- **选项 2**：让"目标分辨率"变成用户的**输入约束**——用户填的目标尺寸精确决定仿射矩阵的缩放因子，从而"显示值"仍是权威的。这更符合"定帧"的产品语义，但要重新推导 `scale`/`aspect_ratio` 与目标尺寸的双向换算。

倾向选项 2，但需要确认它与"锁定目标分辨率"等现有交互（`property_panel.on_t_w_changed` / `on_t_h_changed`）能对齐。

现有测试 `test_scaled_size_matches_effective_target_size` 会在这个不变量被打破时立刻失败——它是有意留下的警报，不是障碍。

### 像素画用户的诉求相反

方案 C 让亚像素平移变得平滑，代价是**边缘必然被插值**。像素画 / 精灵表用户想要的恰恰是整数对齐 + 无插值（最近邻）。

注意应用**已经**提供了"偏移量整数化"（`main_window.integerize_selection_offset`，用 `round()`）。所以合理的分工是：

- 导出器**忠实呈现数据**——position 是分数就平滑渲染，不做隐式取整；
- 想要硬边的用户用"偏移量整数化"把数据变成整数，（未来可选）配合最近邻重采样。

这也顺便消除了一个现存的语义矛盾：**应用自己的"整数化"用 `round()`，而导出器在用户背后用 `int()` 施加了另一套取整规则。**

## 9. 复现实验

本文数据可用下述脚本复现（repo 根目录）。注意用 `(W-1)/2` 作为质心基准，而非 `W/2`。

```python
import os, sys
sys.path.insert(0, os.path.join(os.getcwd(), 'src')); sys.path.insert(0, os.getcwd())
from PIL import Image, ImageDraw
from model.project_data import FrameData
from utils.exporter import Exporter

W, H = 200, 150

def make_disc(path, size):
    """旋转对称夹具：真实质心恒在几何中心，任何漂移都是导出误差。"""
    img = Image.new('RGBA', (size, size), (0, 0, 0, 0))
    m = size / 2 - 0.5
    ImageDraw.Draw(img).ellipse([m-20, m-20, m+20, m+20], fill=(255,)*4)
    img.save(path); return path

def centroid(im):
    a = im.split()[3].load(); tw = tx = ty = 0
    for y in range(im.height):
        for x in range(im.width):
            v = a[x, y]
            if v: tw += v; tx += v*x; ty += v*y
    return (tx/tw, ty/tw) if tw else (None, None)

asset = make_disc('dev/tmp_baseline/assets/disc63.png', 63)
for i in range(11):                      # 实验 A：分数位置
    pos = i * 0.4
    f = FrameData(asset, scale=1.0, position=(pos, 0), rotation=0.0)
    c = Image.new('RGBA', (W, H), (0,)*4)
    Exporter.compose_frame(c, f, W, H)
    cx, _ = centroid(c)
    print(f"pos={pos:4.1f}  质心={cx:7.3f}  偏差={cx-(W-1)/2:+.3f}")
```
